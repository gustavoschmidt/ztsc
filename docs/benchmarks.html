01 · what the inputs are

Two workloads, stated plainly

A type checker faces two very different workloads, and this page measures both — labeled, because they demonstrate different things:

  • Declaration files. The eight-package matrix below checks each package's published .d.ts — the files your dependencies actually ship. This is pure type-level work: generics, conditional and mapped types, huge interface surfaces, declaration merging. There are no function bodies in these inputs, so expression-level inference and control-flow narrowing are exercised only by the embedded standard library that both tools also check. It is the right corpus for "how fast is the type-level machinery" and it is fully reproducible from pinned versions.
  • Application source. The real test of a checker is .ts/.tsx with bodies: inference, narrowing, JSX, the whole expression grammar. A whole application is measured: excalidraw, public and reproducible — anyone can clone it and re-run both tools — and on it ztsc reports exactly the same 17 diagnostics as tsgo, same file, line, column and code, at every checker count from 1 to 8, in 0.35 s / 129.8 MB against tsgo's 0.50 s / 649.5 MB, both at their default four checkers.

The package matrix is not a diagnostic-parity claim: ztsc checks a measured subset of TypeScript, so those are throughput and memory comparisons on identical inputs. Correctness is tracked separately, by the 917-case differential conformance suite and the excalidraw diagnostic convergence.

03 · real application source

A whole application: full .ts/.tsx with bodies

Declaration files never exercise inference on function bodies, narrowing, or JSX. A whole application does — public, pinned, and reproducible by anyone.

excalidraw — public, pinned, reproducible

excalidraw v0.18.1 at commit a2ec2889: a real React/TypeScript app with its node_modules, checked whole. ztsc loads 1,110 files / 332,794 lines (537 of them the project's own source; the rest are the dependency .d.ts closure and the standard library). Both tools at their default 4 checkers:

toolwallpeak RSSdiagnostics
ztsc0.35 s129.8 MBthe same 17 — same file, line, column, code — at every checker count 1–8
tsgo 7.0.20.50 s649.5 MBbaseline: 17 diagnostics

1.4× faster at 20% of the peak memory — and, unlike the package matrix, this row is a diagnostic claim. ztsc reports exactly the same 17 diagnostics as tsgo: the same (file, line, column, code) for every one, zero excess and zero under-reports, and the same set at every checker count from 1 to 8. The message text is not identical — tsgo says Uint8Array<ArrayBufferLike> where ztsc expands the union, and BlobPart where ztsc names its constituents — so this is a same-findings claim, not a byte-identical-output one. It is enforced as a standing gate by bench/convergence.sh, whose false-positive and under-report ceilings both sit at zero.

What the 17 are: excalidraw's own pinned tsc 4.9.4 reports zero errors on this tree. The 17 findings come from TypeScript 7's newer lib definitions: nine are the Uint8Array/ArrayBuffer generic parameters added since 4.9 (ArrayBufferLike no longer collapsing into ArrayBuffer), six are implicit-any reports in one file behind a dependency whose types no longer resolve under its package exports map, and two are ordinary findings (a comparison with no overlap, an event-target mismatch). They are real findings under tsgo's libs, and ztsc agrees with tsgo on all of them.

The config caveat. TypeScript 7 removed moduleResolution: "node10" and baseUrl, so tsgo cannot read excalidraw's real tsconfig.json at all — it stops at two config errors (TS5108, TS5102) having checked nothing. The row therefore uses tsconfig.tsgo.json, a minimal adjustment of the real config that both tools accept: "moduleResolution": "bundler" instead of "node", and baseUrl dropped (the paths entries are already explicit relative paths, so nothing else changes). Everything else is byte-for-byte the project's own config. ztsc reads both files, and its diagnostic set is identical under either — the same 17 keys, and the same 1,110 files / 332,794 lines loaded — so the adjustment changes what tsgo can run, not what is being measured.

04 · parallelism sweep

What happens between 1 and 8 checkers

Both tools default to 4 checker instances, so the headline numbers are defaults-vs-defaults — but sweeping --checkers 1→8 makes the memory story starker. tsgo's RSS climbs steeply with checker count (drizzle-orm: 166 → 411 MB from 1 to 8 checkers) while ztsc's barely moves (15 → 18 MB on the same package) — ztsc's entire 1–8 range stays below tsgo's leanest single-checker run on every package. Since the demand-paged right-sizing of per-checker state, ztsc's RSS doesn't even grow monotonically with N: on the multi corpus the high-water mark is N=4 (~41 MB) and N=8 sits below it (~38 MB).

Speed scales near-linearly to N=4 (3.5×) and tapers at N=8 (4.5×), at the cost of some duplicated type derivation between the independent checker instances — that trade and its measurements are covered in the internals tour. Methodology and reproduction recipes are in BENCHMARKS.md.

07 · methodology

How the numbers are taken — and how to retake them

Protocol. Wall clock is the median of 11 runs, timed with a monotonic nanosecond timer around the whole process — which is what makes the small-package ratios real rather than timer rounding. Peak RSS is the median of 5 runs under /usr/bin/time -l (the "maximum resident set size" line, in bytes). One warm-up per configuration. Both tools at their defaults (4 checker instances), single machine: Apple M4, 10 cores, 32 GB, macOS. tsgo is invoked as its platform binary directly — no Node host in the measurement.

Reproducing. Both tools are one command away — the baseline tsgo is the @typescript/native-preview package on npm:

npm i @typescript/native-preview       # tsgo, the native TS 7 baseline
bench/fetch_real.sh                    # vendor the pinned .d.ts + write tsconfigs
zig build bench                        # ReleaseFast binary -> zig-out/bench/ztsc

C=bench/corpus/real/_types_node_22.7.4
zig-out/bench/ztsc --pretty=false --checkers=4 -p "$C"   # wall: median of 11
/usr/bin/time -l tsgo --noEmit --checkers 4 -p "$C"      # RSS: median of 5

The synthetic-corpus sweep is bench/e2e.sh multi. Full details, per-package sweeps, and run-to-run variance notes are in BENCHMARKS.md.

Read before quoting. The package matrix is throughput and memory on identical inputs — not a diagnostic-parity claim:

ztsc checks a subset of TypeScript (against the real ES-core + DOM lib), so on the packages its diagnostic output differs from tsgo's; correctness is tracked separately by the 917-case differential conformance suite and the excalidraw convergence gate (the same 17 diagnostics as tsgo at every checker count — same file, line, column and code, though not the same message text). Packages are vendored without their dependencies — nonzero exit is expected, and both tools fully parse, bind, and check every file regardless. At the 7–24 ms scale both tools are effectively instant, and the ratio mostly reflects fixed startup costs. Single machine, single OS — no Linux numbers yet.
