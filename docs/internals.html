How ZTSC works

A guided tour of the Zig TypeScript Checker — a type checker (no JS emit) for a strict-mode TypeScript subset. The whole design serves one bet: memory is where a systems language beats a garbage-collected one, and speed follows from the same choices. This page explains how; the numbers themselves live on the benchmarks page.

01 · the architecture

One pass, three parallel regimes

ZTSC is a batch pipeline with three distinct concurrency regimes. First, a parallel front end: files are discovered from the entry points, and each file's front end (load, parse — which tokenizes as it goes — and bind) runs as one task on a worker pool. The import specifiers and triple-slash /// <reference> directives a file surfaces queue new file tasks immediately — no barrier between "waves", so one huge file can't stall the rest of the graph. Second, once discovery drains, a serial resolve + link step builds sealed import/export tables, merges cross-file global declarations, and registers ambient modules. Third, the program is partitioned across N independent checker instances that read everything without locks and never write anything another checker reads.

How the front end coordinates — the honest lock inventory

Discovery is driven by a single-owner completion-queue scheduler: the main thread owns the module graph and the seen-set outright, workers own their file task, and the two sides communicate over an unbounded FIFO channel — a plain mutex-and-condition queue in main.zig. Workers push "file done, here are its import specifiers"; the main thread pops, resolves each specifier (memoized per (importer dir, specifier) with a negative cache, so a bare specifier imported from a hundred files walks node_modules once), and enqueues newly discovered files. No graph state is ever touched by two threads.

So the precise claim is not "no locks anywhere" — it is that locks are confined to two small, cold structures, and the hot paths have none:

  • The completion queue — the mutex-and-condition channel above. Touched once per file, not per node; its buffer lives in its own arena and is only handled under the lock.
  • The string interner — the one shared mutable structure in the program, sharded 16 ways by string hash with a mutex per shard, so two threads contend only when they hash into the same shard at the same moment.
  • Everything else — including the entire check phase — takes no locks at all. The mechanism is immutability boundaries: parse output is frozen before bind reads it, bind output is frozen before check reads it, and the N checkers share only sealed data. There is also no lock hiding in the allocator, because there is no malloc path — allocation is a per-thread arena bump.

The pipeline, as data

Every stage is a pure function from one sealed struct to the next — plain data, slices of integers, produced by exactly one phase, frozen at its seal boundary, read immutably by everything downstream. The handoff chain is the architecture: what a phase is allowed to know is exactly what its input struct holds (ARCHITECTURE.md codifies this as a functional core of pure phase functions around one imperative shell, main.zig, which owns every thread, timer, and arena).

02 · the u32 decision

Why everything is a u32

Every identifier in the system — token index, AST node, interned string (Atom), SymbolId, ScopeId, FlowId, FileId, TypeId — is the same type: a u32 index into a flat array. That is a deliberate point in a three-way trade, and it's worth spelling out because the whole memory story rests on it:

  • Why not u64 (or pointers, which are u64 in disguise)? Doubling the index width doubles every id-bearing array and halves how many ids fit in a 64-byte cache line — 16 as u32, 8 as u64 — for address space no real program needs. Four billion nodes-per-file, types-per-checker, or interned strings is orders of magnitude beyond the largest inputs ztsc will ever see. A 64-bit pointer costs the same 8 bytes and is worse: it pins objects to addresses (so structures can't be relocated or mmap-backed freely) and every dereference is a potential cache miss into scattered heap.
  • Why not u16? It genuinely overflows: 65,535 is smaller than the token count of a single big published file — csstype's one index.d.ts is 21k lines of dense union types, several times that in tokens. Per-file, per-program, and per-checker id spaces all blow through 16 bits on real inputs.
  • Alignment falls out for free. A u32 array is naturally aligned with zero padding, and because storage is struct-of-arrays, mixed-width fields never pad each other either: a node's 1-byte tag lives in a u8 array, its 4-byte token and 8-byte payload in their own arrays — 13 bytes of true data per node instead of a 16-or-24-byte padded struct. When a bit is needed, it's taken from the index itself rather than a new field: bit 31 of a token's start offset is the "newline before" flag that drives ASI, and spare high bits carry similar flags elsewhere — the payload stays one word.
  • Integer ids compose into cache keys. Two u32s pack into one u64, so the assignability memo is keyed on a (TypeId, TypeId) pair packed into a single word, and the binder's duplicate detection keys on (scope << 32) | atom — one hash-map probe, no tuple hashing, no allocation.

The same move is applied to values, not just positions, via interning. A string is looked up once in the global interner and is an Atom forever after — every later name comparison in the binder, linker, and checker is an integer compare, never a byte compare. Types go further: the type store hash-conses every type it builds, so structurally identical types get the same TypeId, type equality is id1 == id2, and every downstream cache (assignability, instantiation, expression types) gets small, uniform integer keys. Section 05 shows that machinery.

The one discipline this buys its costs with: 0 is the universal "none". Node 0 is always the root and the root is never anyone's child, so optional references need no maxInt sentinels and no option types bloating the arrays.

03 · the ast

No pointers, anywhere

The AST is modeled on the Zig compiler's own — a proven data-oriented design. A node is not an object; it is a u32 index. Storage is struct-of-arrays (std.MultiArrayList): three parallel arrays hold each node's tag (1 byte), main token (4 bytes) and a fixed {lhs, rhs} payload (8 bytes). Anything variable-length — statement lists, call arguments, union members — lives in one shared extra_data: []u32 side array that nodes point into by range.

There is no separate tokenize pass — the parser pulls tokens from the scanner as it goes and materializes the token arrays as a side effect. Out-of-subset syntax parses into an unsupported node spanning its token range, tagged with which construct it is (the --census flag feeds on this), paired with a clear diagnostic — never a wrong answer, never a crash (every phase is fuzzed).

04 · the binder

Symbols, scopes and flow — same discipline

The binder produces three things per file, all in the AST's flat-array style: a symbol table, a scope tree, and a control-flow graph that the checker later walks for narrowing. It costs 32.2 bytes per source line, and its output is sealed immutable the moment binding finishes.

  • One hash map per file, not per scope. While binding, inserts and duplicate detection go through a single open-addressed map keyed by (scope << 32) | atom. At seal time members are flattened into two parallel arrays segmented per scope and sorted by atom, so lookup is a binary search costing 8 bytes/member — no per-scope hash-table headers or load-factor waste.
  • tsc-style symbols. One symbol per (scope, name) across value and type space — var x; interface x {} is one symbol with both flags. Conflicts are caught with per-kind "excludes" masks; overloads and interface merging hang off a per-symbol declaration list.
  • The flow graph is antecedent-linked, modeled on tsc: assign, cond_true/cond_false, branch and loop labels. Single-antecedent joins collapse and never allocate. Flow ids attach to identifier reads through a compact sorted (node, flow) map — 8 bytes per reference rather than 4 bytes for every node.
  • Global contributions are pay-per-use. Each file's bind output carries a slice of the names it contributes to the global scope — the whole top level for a script or the lib, only declare global blocks for a module — plus its declare module "spec" ambient blocks. For a typical app module both slices are empty and the linker's cross-file merge skips the file entirely, so @types/node-style declaration merging costs nothing on code that doesn't use it. This layer passed its real-world acceptance test: checking against the actual published @types/node, ztsc's cross-file merge diagnostics match the pinned tsgo 7.0.2 oracle.

05 · types

A type is a u32, too

Types live in a struct-of-arrays store shaped exactly like the AST: a TypeId is a u32 index, fixed payloads sit in parallel arrays, variable payloads (union members, object properties, function params) go in a shared extra array. The crucial move is that types are hash-consed: structurally identical types get the same id. The store is split in two — a shared frozen base (ids below base_len, readable lock-free by every checker) and a per-checker overlay that owns everything else — substrate that made the lib-sharing experiments in the negative-results note cheap to run.

Everything downstream gets cheaper because of this. Well-known types sit at fixed indices (any = 1 … empty_object = 16), so no lookup is needed for the common cases. Unions are canonical at construction — flattened, deduped, never dropped, literals absorbed by their base primitive, true | false collapsed to boolean — which means the checker compares canonical forms, not spellings. Display order is structural rather than TypeId-based, so a rendered union reads the same for any checker count and any id assignment. Named types (interfaces, classes, aliases) stay lazy as .ref {symbol, args} until the checker actually needs their members — which is also why embedding the full 14k-line lib barely moved RSS: only the touched surface ever interns. Object-literal "freshness" for excess-property checks is one flag bit that participates in interning, so no side table is needed.

The checker itself (checker.zig, by far the largest file at 19k lines) implements structural assignability, inference, declared-overload resolution, control-flow narrowing (truthiness, typeof, equality, in, instanceof, discriminants, assignments), user-defined type guards and assertion functions, enums, accessors, as const/satisfies, this-typing, TC39 decorators with signature checks, unique symbol, import() types, instantiation expressions, async/await/Promise typing, the Symbol.iterator protocol, JSX element typing — and the type-level core: conditional types with infer and distributivity, mapped types with as key remapping, template-literal types and the string intrinsics, indexed access and keyof over generics, recursive aliases, and call/construct signatures in interfaces and type literals. Generic instantiation is memoized with depth limits so that machinery can't blow up. All of it matches the TypeScript compiler's observable behavior, verified differentially.

06 · memory

Allocation lifetime = phase lifetime

There is no general-purpose heap churn in ZTSC. The rule, followed everywhere: one arena per lifetime, and no per-object frees, ever. Every structure is bump-allocated into the arena matching its phase, sealed read-only when the phase ends, and released wholesale when the process exits. Since arenas are per-thread, there is no allocator contention either — no locks in the malloc path, because there is no malloc path.

Why this wins against tsgo specifically: Go's collector needs heap headroom (typically ~2× live data), and its AST/type objects carry per-object headers and pointers. ZTSC's live data is its footprint — the entire heap (all arenas plus the interner) for the 93k-line corpus is 19.2 MB, about 187 bytes per source line, all-in. That figure used to be 45.5 MB: a dedicated debt-paydown pass (seal the parser's output into exact-size arrays instead of stranding doubling-realloc slack in the arena, drop a duplicate token scan, reset the resolution scratch per file) cut arena heap by more than half without touching any per-structure cost. Source bytes never even count: files are mmapped read-only and the AST references them by offset; the only copies made are into the string interner.

The same discipline covers the one place a checker's state must span the whole program: its per-symbol arrays (sym_types/sym_state) are ZeroPagedArrays (zeropage.zig) — fixed-length views over fresh MAP_ANONYMOUS pages, the one source where kernel zero-fill is a documented guarantee. The all-zero "not computed" state costs no initialization, and untouched pages never become resident, so a checker's residency tracks its working set, not the program's symbol count. That's why peak RSS no longer grows monotonically with --checkers.

07 · parallelism

N checkers, no shared mutable state, one answer

The front end is embarrassingly parallel: one task per file on a std.Thread.Pool, each task owning its own arenas, coordinated only through the completion queue described in section 01. The interesting part is the check phase, which borrows tsgo's key trick: partition the program's files across N independent checker instances (default min(4, cores), matching tsgo) — by estimated cost (AST node count) and import locality, so one giant file doesn't leave three checkers idle (on the skewed stress corpus the cost-based partition cut check time 26%; on bigfan, 2.4×) and import-adjacent files tend to land on the same checker, which materializes a shared dependency's types once instead of once per checker that reaches it. File ids are BFS positions in the import graph, so contiguous id runs are import-adjacent: the order is cut into equal-weight runs and dealt longest-first onto the least-loaded checker, keeping the locality without letting one checker straggle. The embedded lib files are parsed, bound, linked and — by default — enqueued to a checker just like user code, matching tsc and tsgo, which type-check their default lib at their defaults. Because the shipped lib is pre-verified and its diagnostics are never surfaced, --skip-default-lib-check (tsc's skipDefaultLibCheck; also the tsconfig skipLibCheck / skipDefaultLibCheck keys) drops it back out of the partitions for pure time and memory savings — on zod's DOM config that alone cuts the check phase 2.4×.

During the check phase itself, a checker takes no locks: each owns a private type store and private caches, writes nothing any other checker reads, and reads only the sealed AST/binder/link data. The cost of that independence is duplicated inference: when two checkers' partitions both import the same file, each re-derives the types of the exports it touches — the linker's sealed tables tell every checker where an import points, but the meaning of that target is computed per checker, lazily, in its own store. That duplication is the project's main speed/memory dial, and it is measured rather than guessed:

Sharing a type store between checkers would erase that duplication — and it was seriously designed and then measured out: only about a quarter of types are shareable in principle, the savings are noise at this scale, and the price would be synchronization on the hottest structure in the program. The rationale's negative-results section keeps that record.

Determinism is a hard guarantee, not a hope: every diagnostic is tagged with its file, each file is checked by exactly one checker, output is printed per file in discovery order, position-sorted, and even rendered type display order is structural rather than id-dependent. The conformance suite asserts byte-identical output for any N — and a standing repeat-run gate asserts the checker's work counters don't depend on traversal order either, which is what makes the parallelism dial honest.

08 · synthesis

Why it's fast (and small)

Nothing in ZTSC is exotic. The performance comes from five decisions applied with total consistency — the same discipline in the AST, the binder, the types and the module graph:

  • Indices, not pointers. Every structure is flat arrays addressed by u32. Half the memory of a 64-bit pointer, and traversals stream through cache lines instead of chasing the heap.
  • Struct-of-arrays. A pass that only needs node tags touches a 1-byte-per-node array and nothing else. 16 B/node vs 100–200+ for object ASTs.
  • Arenas, no frees, no GC. Allocation is a pointer bump; deallocation is free; footprint equals live data — no collector headroom, no per-object headers.
  • Intern everything, compare integers. Strings become atoms once; types become TypeIds once. Equality checks and cache keys are integer compares for the rest of the run.
  • Seal, then share. Each phase's output is frozen before the next phase reads it — so the check phase runs without a single lock, and the front end's only locks are the completion queue and the sharded interner.

Notice these reinforce each other: interning only works cheaply because types are immutable; immutability is natural because arenas never free; lock-free checking is safe because everything is sealed; and small nodes are possible because indices replaced pointers. It's one idea — data-oriented design — expressed five ways. Laziness is the sixth, quieter decision: named types expand only when touched, per-symbol state pages in only when faulted — which is how embedding the real 14k-line lib costs almost nothing on a project that uses a fraction of it.

What's left is the ship itself: v0.0.1 as a working bunx ztsc.
