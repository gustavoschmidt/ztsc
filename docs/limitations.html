limitations · v0.0.1-dev · pre-release

What it doesn't do yet

ztsc is not ready for production use, and this page is the precise version of that sentence: what's missing, how each gap behaves today, and what's planned. The rule that governs every gap: fail in the safe direction — miss an error tsc would report rather than invent one, and never crash.

01 · the contract

A measured subset, safely bounded

ztsc checks a large, well-defined subset of strict-mode TypeScript: the full type-level language (conditional types with infer, mapped types, template-literal types, generics, narrowing, declaration merging), the real ES-core…esnext + DOM standard library with the full iteration protocol, CommonJS interop, instantiation expressions, const-symbol computed keys, and JSX against the real @types/react. What it checks, it checks like the TypeScript compiler — enforced by a 991-case differential conformance suite validated against the pinned native tsgo 7.0.2, down to error codes and lines.

Everything outside the subset is bounded by three guarantees:

  • Unsupported syntax never lies. Out-of-subset constructs parse into an explicit unsupported node with a clear "not yet supported" diagnostic — never a wrong answer, never a crash (every phase is fuzzed).
  • Known gaps under-report. Where ztsc can't yet reproduce an error, it stays silent rather than erroring on valid code. That bias holds but is not yet absolute — see the false-positive ledger below.
  • You can measure your own project. ztsc --census prints a frequency table of exactly which unsupported constructs your codebase contains, so "is my project in the subset?" is one command, not a guess.

How close is it to a drop-in tsc --noEmit? Measured on a whole application. On excalidraw — public, pinned, checked with its node_modules — ztsc reports exactly the same 17 diagnostics as tsgo 7.0.2, same file, line, column and code, at every checker count from 1 to 8: nothing extra, nothing missing.

02 · the big gaps

Platform and modes — all planned

gaptodayplan
Windows does not build or run — a Windows target fails at compile time with a clear error port planned. The checker's per-symbol state lives in demand-zeroed anonymous memory via POSIX mmap (untouched pages never become resident — load-bearing for the memory numbers); Windows has an exact equivalent (VirtualAlloc) that isn't wired in yet. macOS and Linux work today.
Watch mode batch only — check, print, exit planned next. Every phase's output is an immutable sealed artifact per file, which is exactly the granularity a watch mode invalidates.
LSP none — the batch CLI is the interface planned after watch mode, on the same sealed-phase substrate an editor queries.
npm distribution build from source (usage) v0.0.1 ships as bunx ztsc / npx ztsc — a single static binary per platform, no install step.

03 · false positives

Zero on the application benchmark

The number that matters most for trust is not estimated — it is measured continuously on a real application, against the pinned oracle.

On excalidraw — the public, pinned application benchmark, checked whole with its node_modules — the count is zero. ztsc reports exactly the same 17 diagnostics as tsgo 7.0.2: the same file, line, column and code for every one, no diagnostic tsgo does not also report, and none of tsgo's missing — at every checker count from 1 to 8. That is a standing gate (bench/convergence.sh), with the false-positive and under-report ceilings both pinned at zero, so a regression fails the build rather than being noticed later. The message text still differs from tsgo's in places, so this is a same-findings result, not a byte-identical-output one.

Everything else on this page is an under-report — a missed error, not a false alarm. For an agent or CI gate, that asymmetry is deliberate: a bogus error sends a machine off to "fix" correct code; a missed error is caught by the next tool in the chain. The rationale covers why that contract is the design center.

04 · the smaller gaps

Known leniencies, each in the safe direction

  • tsconfig options beyond the subset — honored: files / include / exclude / extends, and the compilerOptions keys lib, baseUrl, paths, types, typeRoots, skipLibCheck / skipDefaultLibCheck, allowJs, esModuleInterop, allowSyntheticDefaultImports, noImplicitAny, resolveJsonModule. Strict mode only (strict: false is refused); everything else is accepted and ignored, and --verbose lists which.
  • lib families other than es* and dom* (e.g. webworker) — ignored, with a note under --verbose.
  • Generator corners — yield* delegation is unchecked, and unannotated generator functions type as any (the full iteration protocol — for…of over every DOM collection, for await with the sync-iterable fallback — is checked).
  • CommonJS corners — a namespace import of an export = module keeps the export's call signature, so ns() is not flagged.
  • Symbol-key corners — a plain non-unique symbol key (rxjs's [Symbol.observable]) is keyed by name rather than as a symbol index; a deeper-qualified [a.b.c] computed key stays out of subset.
  • JSX corners — prop type mismatches arriving inside a spread object, spreads of unions/generics/index-signature types, and children value typing are unchecked; class-component prop mistakes report refined codes where tsgo reports TS2769.
  • Class-value instantiation expressions — typeof C<T> applied to a class value under-reports.
  • Other known edge cases miss an error the TypeScript compiler would report; the conformance suite's DEFERRED ledger tracks 13 accepted divergences explicitly — with a written justification each — rather than hiding them in the goldens, and the runner fails a case whose entry stops describing reality, so the ledger cannot be used to mask a regression. Every one is an under-report. The only whole check simply not implemented is TS2578 (unused @ts-expect-error — only sound on a checker that reports everything the oracle does). The rest are deliberate trades where the stricter rule was measured to cost false positives on correct code — TS2589 at the recursion cap, TS2345 on whole-list rest-union calls (needs const type parameters first), TS2352 on deferred-indexed-access casts, TS2322 on the exclusive callback-variance rule, TS7053 for a number-literal key that names no member, and TS2344/TS2741 for a type argument judged against a structural constraint (the verdict would be only as good as the structural relation, which is not yet exact enough to be the sole evidence for an error — a set constraint such as keyof T & string or "a" | "b" is checked).

Check your own codebase in one command. ztsc --census tallies every out-of-subset construct in your project by frequency — the same instrument that decided what got built first. If the census reads zero and the tsconfig subset covers you, ztsc checks your project today.
